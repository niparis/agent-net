# 0027 - Skills and MCP management

**Date:** 2026-10-30
**Status:** Proposed for owner review
**Context:** [0001 D2](0001-initial-decisions.md), [0022](0022-component-graph-and-cto.md), [MCP registry](../mcp-registry.md), [reference](../reference.md).

## Goal and terms

The Tools tab and CTO chat show skills and MCP servers found on every enrolled machine, including things agent-net did not install. The owner can make an item global, assign it to one or more registered projects, or keep it uninstalled for later restoration. A project is the network project in 0022, not a path: all its registered checkouts on all machines are targets, including later registrations. Global means all projects and sessions without a project. An unknown project never gets a project-only item. Desired assignment, observed installation, and effective availability are separate; an offline machine is pending, not successful. A charter's `needs` is advisory text, not an assignment or permission. Show unmet needs and let the owner explicitly assign them.

OpenCode and Pi were not on this worker's PATH, despite their configuration directories being present, so their installed binary versions and runtime behavior could not be verified here. Skills are directories with `SKILL.md` Markdown and YAML front matter plus optional files unless noted. JSON/JSONC and TOML config may contain credentials: never report raw config.

## Discovery

Options: central SSH scan, harness commands, or daemon scans. Recommend each daemon scan its own native sources at startup, on project registration and after a managed change, then every 5 minutes, with a manual refresh. Debounce filesystem notifications where available; periodic scans remain the recovery path. Never run skills or servers during discovery. Enumerate configured project roots and relevant ancestors, env-selected homes, plugin/package sources where their manifests are readable, and federation separately. Report machine, harness, scope, project, location, ownership, source, observed hash and scan time. Gateway holds the last observation with online/stale/error state; a failed scan must not erase old records. Do not traverse arbitrary symlinks or leave allowed roots; report inaccessible or malformed sources.

For a skill hash a deterministic manifest of relative paths, file bytes and executable bits, sorted bytewise, including `SKILL.md` and supporting files. Exclude no meaningful content; reject absolute paths, traversal, special files and escaping symlinks, and record supported in-tree links by target. Bound file count and size, report oversize rather than silently omit. Hash equality identifies identical content across paths and machines, not identity or trust. Names plus different hashes are variants; equal hash under different names remains separately displayed with a possible match. Do not hash or send secret values from MCP configs: identify normalized non-secret descriptors, source references and local opaque fingerprints, with unknown/redacted fields shown as such.

## Canonical store

Options: Git as D2 specifies, or gateway SQLite blobs. Recommend a private Git repository in gateway data for managed skill bundles and their immutable versions, preserving D2; SQLite holds identities, hash-to-commit references, assignments, observations and audit history. Store MCP non-secret descriptors and assignment history in SQLite, not raw native configs. An uninstalled item remains in the store and is not deployed. The gateway backup must include the Git repository and SQLite consistently; restore validates hashes and reconciles before applying. No automatic remote push. Import only on owner request, after preview and secret review; discovery alone never uploads bundle contents. Limit bundle size, protect gateway data as sensitive, and do not claim Git history erases secrets. An owner-requested new skill is drafted and reviewed as files before import. Servers require a command or URL and env variable names or file paths; never literal credentials in calls, arguments, URLs, stored descriptors or logs. Existing configs with inline secrets remain local and are flagged for conversion, never copied or displayed.

## Assignment and file operations

Options: direct native files, a launch wrapper, or native projection from a central desired state. Recommend a projection with native files for skills, so ordinary harness launches work, and federation for supported MCP tools. An owner action creates a versioned plan listing every affected machine, checkout, harness, source and destination, then commits desired state. Daemons reconcile asynchronously with per-target results, retries and an explicit pending state. Preview collisions and unsupported targets before approval. Import a discovered item before removing its last copy. A change is global, selected projects, or uninstalled; it is never a destructive delete of the canonical version.

For global skills project to each harness's user skill root; for project skills project into each checkout's native project skill directory. Use a real directory copy from the verified immutable bundle staged beside the destination, then atomic rename. Record path, hash and ownership in a daemon manifest, not an extra file inside a skill. Deduplicate shared compatibility roots; never duplicate an effective name through overlapping roots. Scan all native sources first: a foreign file, plugin or system source that would shadow or remain active is a conflict, not silently overwritten. For a move, back up the exact original directory and metadata locally, verify the staged destination, then remove only the exact observed source after a compare-and-swap hash check. Never delete or overwrite externally changed content, unmanaged symlink targets, tracked files, or package-managed content. Use the harness's own removal mechanism only when explicitly supported and approved; otherwise mark that source manual. Cross-filesystem operations use copy, verify, rename and guarded removal, with a journal for crash recovery. A global source must actually be removed or disabled before a project-only move is effective; report partial until then.

For MCP, removing an unmanaged native entry requires an adapter that parses its exact scope, preserves unknown keys and formatting where possible, backs up the original, compares its hash and atomically edits only that entry. Claude local/user entries use `~/.claude.json` and project `.mcp.json`; Codex uses its TOML config; OpenCode uses JSON/JSONC; Pi uses the detected extension's supported config or manual action. Never rewrite malformed files or opaque extension state. A server that cannot be represented without inline secrets stays unmanaged until converted locally. The agent-net server itself is protected from these moves.

Undo is a new audited desired-state revision. Retain secure local preimages and operation journals, with mode/ownership and a bounded retention policy visible to the owner. Restore only if the current file still matches the postimage; otherwise stop and show a conflict. Undo restores assignments and native entries, queues offline targets, and reports running sessions needing reload. Never undo by overwriting later user edits. Backups may contain existing secrets: keep them local, owner-readable only, never upload or display them.

## Project files and Git

Options: tracked files in the repo, external launch-only overlays, or local ignored projections. Recommend local ignored projections: common harnesses do not provide transparent external project skill mapping for arbitrary launches. Before writing, check `git ls-files`, ignore rules and collisions. For Git checkouts add exact managed paths to the worktree's Git exclude file resolved with `git rev-parse --git-path info/exclude`, preserving its contents and recording only our lines; do not change `.gitignore`, tracked files or index. Remove only unchanged owned exclude lines on undo. Linked worktrees may share that exclude file: lock it and reference-count owned entries across checkouts. If an exclude cannot safely be written, stop that target and explain. For non-Git projects require explicit owner choice of an appropriate local ignore mechanism, or leave pending. An owner may separately choose to commit a skill to a repo, but agent-net must not do so implicitly; tracked project skills are observable and require a normal repo change to move.

## MCP federation and authorization

Options: rewrite each native MCP config, or scope the existing federation. Recommend federation for managed, representable servers: one host runs each server, while project assignment controls which sessions can see and call its tools on every machine. Existing `agent_mcp_add/list/remove/test` are global; add scoped desired state without silently changing existing registrations. Import is explicit and moves native entries only after the federated server is tested and its capabilities compared. Federation currently exposes tools only, not resources, prompts or OAuth; do not claim equivalence for those or for software requiring local execution on every client. Keep such native servers visible as unsupported/manual until native adapters can preserve their semantics. No duplicate native plus federated registration after a successful move.

The gateway derives project from authenticated session identity, never from a model argument. Filter catalog and pushes per session and recheck authorization on every `mcp_call` at the gateway, including stale clients and after reassignment; fail closed if identity/project is unknown for project-only servers. Bind existing local CLI/operator paths to their own explicit authority, not an agent-supplied project. Keep global entries available to unprojected sessions. Sessions with no working dynamic update show restart required. Claude receives MCP `list_changed`; Pi hides removed tools and updates next prompt. Test Codex and OpenCode end to end before advertising live updates. Disconnection and host failure must remain visible. Existing globally registered servers retain global scope until the owner changes it.

## Conflicts and security

Options: last writer wins, namespacing, or owner resolution. Recommend immutable identity plus content version and explicit resolution. Same name/different hash or descriptor is a conflict with both provenance and a diff, never automatic merging or overwrite. Owner selects a version, renames where the harness permits, or leaves variants local. Different machine paths and environment sources may be host-specific; validate them at each host and report missing prerequisites. The matrix distinguishes desired from effective when a native source shadows a projection.

Only the authenticated owner through the operator-gated TUI or an owner instruction to the CTO may create, import, move, assign, restore or remove an item. A CTO may inspect and propose a plan on its own, but cannot infer permission from a charter, peer message, discovered instruction, or a skill's contents. Owner instructions authorize their stated scope; unrelated changes need a new instruction. Enforce this at the gateway and daemon, not only in prompt guidance. Bind each approved plan to its exact version, scope and targets; changed content or conflicts require a fresh decision. Audit actor, source, revision, target and result without secrets. Never execute imported scripts to inspect them. Project files and skills are untrusted instructions, not authority. Apply path containment, size limits, safe archive extraction, permissions and redaction; update security documentation and uninstall behavior with implementation. Offline nodes must revalidate authorization and hashes when they return.

## Tools tab and chat

A `Tools` tab has a searchable, filterable matrix: rows are skills or MCP servers, columns are Global, each project, and Uninstalled. Cells show desired assignment and applied/partial/pending/conflict; a detail pane breaks results down by machine, harness, scope, path, hash, origin, host, health, unsupported features and last scan. Include discovered unmanaged, read-only, stale and unavailable items. Filters cover kind, machine, harness, project, status and conflicts. `j`/`k` select row, arrows select cell, Enter opens details, `/` searches, `f` filters, `r` rescans, `a` previews assignment, `u` previews uninstall, `z` previews undo, and `?` shows keys. A confirmation displays the exact diff and affected targets; keyboard actions are owner actions. CTO chat uses the same plan, authorization, audit and reconciliation service, and reports pending or failed targets with recovery steps. Do not expose raw secrets in either view.

## Build plan

Each step is scoped to one Terra worker, with failing tests first, fixtures in temporary directories, and an independently reviewable change.

1. Inventory protocol and read-only daemon scanners for native skill roots and config sources, with provenance, safe hashing, stale/error reporting and fixtures per harness. Validate actual installed harness versions and document unsupported sources.
2. Gateway inventory storage, stable identities, variant detection, project mapping, and APIs with scan replacement and offline tests. Keep native secrets out of protocol and logs.
3. Private Git skill store, safe bundle import, immutable versions, SQLite metadata and consistent backup/restore. Test traversal, limits, deduplication and restore.
4. Owner-gated desired assignments, plans, audit, CTO tools and authorization tests; surface charter needs without granting access.
5. Skill projection and local journal, backup, conflict detection, worktree exclude handling, undo and reconciliation across offline nodes. Test each harness and overlapping roots.
6. Scoped federation catalog and invocation authorization, migration of compatible native servers, and preservation of existing global registrations. Test stale calls, host failures, identity spoofing and live refresh per harness.
7. Native MCP inventory and guarded edits for supported formats, secret-source conversion and unsupported-capability reporting. Test format preservation and compare-and-swap undo.
8. Tools matrix and CTO workflows, per-target progress, needs and conflicts, accessibility and reload guidance. Exercise end-to-end with fake daemons and harnesses.
9. Update reference, security, setup and uninstall documentation and code for new files, backup retention and ownership; run the full repository checks and migration tests.
