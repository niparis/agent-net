# Sandbox for OpenCode and Pi workers

Status: proposed design, not implemented. Research on 2026-11-01. Decision [0020](../decisions/0020-worker-sandbox.md) defines the owner-selected levels. This proposal does not change Codex or Claude workers.

## Evidence

OpenCode's [v2 permissions documentation](https://opencode.ai/v2/docs/permissions/) says that shell runs with the host user's filesystem, process and network authority and directory inference is best effort. Its rules are not a containment boundary. Pi also needs an OS boundary around the entire worker, not just tool calls.

On the research machine, Ubuntu 24.04.3, x86-64, kernel `6.8.0-137-generic`:

- `bwrap --version` returned 0.9.0. `apt-cache policy bubblewrap` showed installed and candidate version `0.9.0-1ubuntu0.3` from Ubuntu's packages. It is already installed here; on another machine installation may need an administrator. A temporary-directory probe using `bwrap --ro-bind / / --bind "$work" "$work" -- sh ...` wrote in `work` and got `Read-only file system` on a sibling. This is a basic mount test, not an escape test.
- `/proc/sys/kernel/apparmor_restrict_unprivileged_userns` was `0` and `/proc/sys/kernel/unprivileged_userns_clone` was `1`. `unshare -Ur true` succeeded. These are host-specific results; Ubuntu AppArmor policy, container policy, or a future setting can prevent this elsewhere.
- `landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION)` returned ABI 4. The [kernel documentation](https://docs.kernel.org/6.8/userspace-api/landlock.html) describes inherited filesystem restrictions. ABI 4 can restrict TCP bind and connect, but cannot by itself block UDP or all IPC. [go-landlock](https://github.com/landlock-lsm/go-landlock) is a possible pure Go library. A small single-threaded helper can instead install Landlock and seccomp before `exec`. Do not install a thread-local restriction on an arbitrary Go runtime thread and assume the whole process is covered. Landlock cannot reopen a read-only child beneath a broadly writable parent, so the protected `.git` and other carveouts need careful treatment.
- `systemd-run --version` reported 255. A `systemd-run --user --wait --pipe` probe with `PrivateUsers=yes`, `ProtectSystem=strict`, `ReadWritePaths=<temporary work dir>` and `PrivateNetwork=yes` ran `/bin/true`. It did not test denials or a worker, and it used the existing session bus despite a temporary `XDG_RUNTIME_DIR`. It is not proof of an isolated user manager. [systemd.exec](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html) documents these mount and network properties and their user-namespace dependency. A user manager and bus are not assured on headless hosts, and a transient unit complicates process ownership, pipes, cleanup and portability.

Codex CLI here was `codex-cli 0.163.0`. `codex sandbox --help` accepts a command and `-P/--permission-profile`; `codex debug --help` did not list `landlock` or `seatbelt` in this version. In a temporary home, `codex sandbox -C <work> -c 'sandbox_mode="workspace-write"' -- ...` failed because a permission profile was required. Retrying with `-P :workspace` failed while building its bubblewrap command: `app-server socket directory must be a user-owned directory with mode 0700`, even with a private mode-0700 runtime directory. No command ran. Therefore wrapping an arbitrary worker is a plausible interface, not a verified solution here. The CLI and profile interface can change, and requiring Codex just to run another harness is undesirable. [Codex core](https://github.com/openai/codex/blob/main/codex-rs/core/README.md) describes its Linux bubblewrap and legacy Landlock paths and its macOS Seatbelt profile. Decision 0020 records successful tests of the separate app-server API and narrow git roots.

On macOS, Codex invokes `/usr/bin/sandbox-exec` with a Seatbelt profile. Apple's [developer forum](https://developer.apple.com/forums/tags/app-sandbox) confirms `sandbox-exec` is deprecated. Its presence and behavior were not tested on a Mac in this research. Check both at launch and in Mac CI. Seatbelt profile syntax is not a stable public API. The [Codex source](https://github.com/openai/codex/blob/main/codex-rs/cli/src/debug_sandbox.rs) is an implementation reference, not a promise of compatibility.

## Boundary and levels

Use bubblewrap on Linux and Seatbelt via `/usr/bin/sandbox-exec` on macOS. Both wrap the harness process itself, so shell commands, language servers and MCP children inherit the boundary. Resolve and validate paths before launch. Never fall back to an unsandboxed worker if a required feature is absent or setup fails. Report the failure and the remedy to the owner. Probe the actual policy, not only executable presence, before advertising enforcement.

| Level | Project and git writes | Network |
| --- | --- | --- |
| `sandboxed` | Worktree and narrow git roots below | On |
| `no-network` | Same | Off |
| `read-only` | None | On |

All levels need a private writable runtime/state directory and private temporary and cache directories for the harness itself. This is an explicit operational exception to decision 0020's read-only wording: no writes to project or host data, but the harness must be able to run. Model output can still be saved in this private state. The owner must accept this clarification before implementation. Set `HOME` or the harness-specific XDG and Pi paths to private locations, and provide only the required configuration and credentials by a controlled copy or read-only input. Never expose the daemon's full state directory as writable. Access to host configuration or credentials is read access, not protection against exfiltration when network is on.

The worktree and its repository must be readable. Use private `GOCACHE` and `GOTMPDIR` under the worker runtime, and a private `TMPDIR`. Do not give write access to the owner's shared Go cache. Build dependencies may need read access to the module cache or network. Ensure the required executables, dynamic libraries, certificates and model credentials are readable. A broad read-only host view matches Codex's current write boundary but exposes secrets to the worker; this is not a confidentiality sandbox.

For a linked worktree, allow writes only to its resolved git administrative directory and the common git directory's `objects`, `refs` and `logs`, as in `codexGitRoots`. Keep the worktree's `.git` pointer and other protected control files read-only even though the worktree is writable. Mount or profile these carveouts explicitly, including nested `.git` and `.codex` paths, and test symlinks, rename and hard-link cases. Do not grant the common git directory as a whole: hooks and config must remain read-only. Shared refs and objects are still mutable repository state, so this is not full protection from malicious git operations. `git gc`, `pack-refs`, branch rename and commits in `isolation: none` can fail. `read-only` gets no git write roots.

## Launch and integration

The daemon creates the private directories and resolves the worktree, actual git paths and writable roots before starting a worker. On Linux, run bubblewrap with a read-only root view, explicit writable binds, protected submounts, a private PID namespace and fresh `/proc`, `--die-with-parent`, and no inherited sensitive descriptors. Use a private network namespace for `no-network`; do not rely on Landlock ABI 4 to block UDP. On macOS, compile a Seatbelt profile that grants reads and only the explicit writes, with network rules per level. Quote profile parameters safely and validate canonical paths. In both cases, prevent process inspection or signaling and IPC to unsandboxed same-user processes where the OS can enforce it; test these properties rather than assuming read-only mounts provide them. If the required boundary cannot be established, fail closed. Symlink races, writable filesystem mounts, inherited descriptors, privileged helpers and host IPC are part of the threat model.

OpenCode currently starts its own server and the daemon talks to it. A private network namespace also isolates loopback, so an outside daemon cannot reach the worker's TCP server. Prefer a supported Unix socket or stdio transport with a narrowly scoped daemon-owned relay outside the namespace; verify the installed OpenCode version supports it. Otherwise the no-network level must fail with an actionable unsupported-transport error until such a transport exists. Do not turn on host networking as a workaround. Pi's RPC pipes must likewise pass through the wrapper, preserving process-group stop, timeout, resume and exit handling. MCP servers launched by either harness inherit the policy and may fail when they need host writes or network. A server reached through a pre-existing host socket or a network service runs outside the boundary and can act with its own authority. Prevent such access for no-network or explicitly reject configurations that cannot be confined.

The agent-net socket is a privileged host IPC channel, not a harmless file. Workers do not need agent-net tools to return a result; disable them and do not expose the socket by default. If a future worker needs it, use an authenticated, narrowly scoped proxy and review its operations as an escape route. A no-network worker cannot call a remote model API itself. It needs a separately designed narrow model relay, or must fail when its model is remote. Do not describe a general network proxy as no-network. A local model also needs a reviewed transport. Private network namespaces alone do not block filesystem Unix sockets or all host IPC; hide or deny those channels, including abstract sockets and inherited file descriptors, and verify on each OS. If this cannot be enforced, do not claim no-network.

## Failure reporting

Use a dedicated setup handshake or error pipe from the launcher before the harness starts. Report the OS, selected level, failed setup step and a short actionable reason in the start error and worker notice. Do not claim the worker ran sandboxed after setup failure. Exit status or stderr from a normal command cannot reliably distinguish sandbox denials from ordinary permission errors. Capture bounded, redacted harness output and report a suspected denial only when there is direct evidence; otherwise report the command failure without asserting its cause. Seatbelt logs and Linux audit logs may be unavailable or privileged, so do not require them for correctness or promise a complete denial count. On unsupported kernels, absent bwrap, denied namespaces, failed profile compilation or missing transport, fail closed and report the specific condition. Preserve the level across follow-ups, including daemon restart.

## Verification and delivery

Use fake harnesses and temporary repositories, homes, sockets and credentials; no paid model calls. Integration tests on Linux and macOS must exercise all three levels and actual child and grandchild processes. Assert allowed worktree and private-state writes, blocked sibling and git config/hook writes, allowed linked-worktree commit, blocked read-only project writes, protected nested paths and symlink/rename/hard-link attacks. Test TCP and UDP, IPv4 and IPv6, DNS, loopback, pathname and abstract Unix sockets, inherited descriptors, host processes, and MCP descendants. Verify model and daemon transport separately. Test startup failure, no fallback, notices, process cleanup, follow-up and restart. Include kernels and macOS versions supported by the release, plus namespace-disabled and missing-tool cases. Skip unavailable platform tests with a clear reason; do not treat a skip as evidence of enforcement.

Parts sized for separate workers:

1. Specify and test a shared policy and launch contract, private paths, failure handshake and notices, without claiming enforcement.
2. Implement the Linux launcher and adversarial filesystem, process and network tests, including capability probes and fail-closed paths.
3. Implement the macOS Seatbelt launcher and equivalent Mac tests, including OS-version checks.
4. Integrate OpenCode and Pi lifecycle, private configuration and supported IPC; test all levels with fake harnesses. Gate no-network until its transport is demonstrably isolated.
5. Update setup, uninstall, reference and security docs as applicable; run the full cross-platform matrix and remove the unenforced notice only for combinations proven to work.

## Owner decisions

- Allow private runtime writes in `read-only`? Recommend yes, with no project or shared host writes. Without it the harness may not start.
- Require bubblewrap on Linux? Recommend yes, with a clear install instruction and fail-closed behavior. Do not silently switch to weaker Landlock or unsandboxed execution.
- Permit no-network remote-model workers through a model-only relay? Recommend defer the relay and fail clearly until its protocol and security are designed. A model relay is an intentional network exception.
- Allow broad host reads and network for the default? Recommend retain decision 0020's semantics and explicitly document secret exposure. A restricted-read or domain-allowlisted policy is a separate owner decision.
- Permit writes to common git refs and objects? Recommend retain the existing narrow roots for worktree commits, with the residual shared-repository risk stated. Offer a future patch-only mode if stronger isolation is wanted.
- Support deprecated Seatbelt? Recommend yes while it works on supported macOS versions, with real Mac tests and fail-closed checks. Revisit if Apple removes it.
