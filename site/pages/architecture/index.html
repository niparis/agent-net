agent-net architecture

What agent-net is

agent-net connects AI coding agents (Claude Code, Codex, OpenCode, Pi, agy) running on several machines, so they work as one team for one person, the owner. You talk to one assistant, the CTO, and it runs the network for you: machines, projects, leads, workers and settings. The agents plan, build, review and ship; you decide what only you can decide.

It is one Go binary, self-hosted, with SQLite built in. It is not a framework for building agents, not a hosted service, and not for teams of people: every machine belongs to one owner.

What makes it different

  1. One network and one tool set for five harnesses. Claude Code, Codex, OpenCode, Pi and Antigravity all get the same agent_* tools.
  2. It joins the sessions you already run, on every machine. Codex threads go through the app server, OpenCode through a plugin inside its service, and an offline Claude Code session is woken with claude --bg.
  3. Models are chosen by expected cost per accepted result, with quota pace, protected subscriptions and a track record per difficulty level. Quota reads never refresh a login. See how it chooses.
  4. Every change has delivery steps, each with an owner, a merger session, and CI as the single test gate. Each change leaves evidence. See how changes leave evidence.

Isn't a swarm fragile?

Many agents sharing one task do conflict and waste tokens. A supervised swarm is built the other way:

  • Each agent owns its piece. One session per project, or one worker per task, with its own context and its own git branch. Two agents do not edit the same thing at once.
  • Agents talk where their work meets. When a change crosses projects, one session tells the other, the way two engineers on two services do. A worker gets a written brief and hands back a checked report, not a shared transcript.
  • Every change in the pipeline is checked before it merges. Accept, test, merge, release and verify each have an owner, riskier changes get a review, and a merger session can own the tests and the merge.
  • Cost is chosen. Each task goes to the cheapest model that is good enough for it, spread across your subscriptions.
  • You supervise by exception. Leads answer their members, the chief of staff sorts the rest, and only real decisions reach your Desk.

Quick start

Your first day with agent-net, step by step.

One idea runs through all of it: you talk to the CTO, and the CTO runs the network. The CTO is your main assistant session. It adds machines, sets up projects, starts and stops sessions, changes settings and answers "where are we?". You use the TUI to watch, and to open a session when you want to look inside it.

Two kinds of sessions

A session is one AI coding agent at work: Claude Code, Codex, OpenCode, Pi or agy. agent-net works with two kinds:

  • Your own sessions. You start them in your terminal, the way you always do (claude, codex, opencode and so on). agent-net finds them by itself and gives them its tools, so they can send and receive messages and start workers. They live as long as your terminal. Use them when you want to work hands-on with one agent.
  • agent-net sessions. agent-net starts them in the background, on any machine: the CTO, the chief of staff, a lead you ask the CTO to start, and every worker. They need no terminal and keep working while you are away. A message to one that stopped wakes it in the same conversation.

Both kinds show up in the Sessions tab and talk to each other the same way. Press Enter on any session to look inside it.

1. Install on your main machine

curl -fsSL https://niparis.github.io/agent-net/install | sh

The script checks the release signature, installs agent-net in ~/.local/bin and sets this machine up as the gateway. If ~/.local/bin is not on your PATH, it prints the line to add. Details and options: setup.md.

2. Open agent-net and meet the CTO

agent-net

The TUI opens on the Sessions tab: your machine and the agent sessions running on it. Press c to open the CTO. From now on, most things start with a sentence to the CTO.

3. Add your other machines (optional)

On the gateway machine, run:

agent-net invite

It prints one install line, valid for 10 minutes and one machine. If the gateway has a Tailscale address, it prints a second line for that address. Paste the line in a shell on the new machine. The new machine shows up in the Sessions tab, and its sessions can now talk to every other session.

Repeat for each machine. Details: setup.md.

4. Set up your projects and teams

Tell the CTO what you work on and how it should be run. These are real first-day asks, lightly edited. Each one sets up something you will not have to manage again:

  • "Start a new project named shop." Why: agent-net only works with projects it knows. A project gets a repo, a place on a machine, and sessions that belong to it.
  • "Create a new project on the worker VM named shop-api, in the same folder as shop. Also create a team with shop, this new project and the finance project." Why: a team groups the projects that change together, so one lead can coordinate them.
  • "I want a second team, the homelab team, with all the sessions we have and a lead." Why: a lead is the one agent you talk to for a team or a repo. It plans, starts workers, checks their work and answers for it.
  • "Help me set up a charter and edges for shop." Why: the charter says what the agent does, accepts and refuses. Edges say who may ask whom for what, so agents can work together without asking you.
  • "Set up the edge between shop and homelab so that homelab deploys shop without my confirmation." Why: every confirmation you give once by rule is one you never give again.
  • "Set up a merger agent for shop." Why: the merger tests, merges and releases changes, so nothing reaches main unchecked and you do not merge by hand.
  • "What workers could I create with agy?", then "Create a new worker type: claude, sonnet, high effort." Why: worker types are the menu the picker chooses from for every task.
  • "I want to replace my homelab lead with a Claude Sonnet session. What is the best way to go about it?" Why: roles stay; the agent program and model behind them can change.

If you already run many sessions and repos, the same asks work on what you have: the CTO places existing sessions into projects and teams.

5. Design the work with the lead

The way to work with a lead is to design with it, not to pass it a one-line order. Open the lead's session (Enter on the Sessions tab) and think the work through together:

  • Say what you want and why. The lead knows its repo: it reads the code, proposes a plan, points out what will break and asks what it needs to know.
  • Push back and refine until the plan is right. A good lead writes the plan down in the repo, so it survives a restart and other agents can read it.
  • Agree on what "done" means, then let it run.

From there the lead works on its own. It splits the plan into tasks and starts workers: short-lived sessions that each do one task in their own branch and sandbox, then hand back. agent-net picks the agent program, model and machine for each worker. The lead reviews what comes back, and each change goes through its steps (accept, review, test, merge, release, verify) until it ships. You get short outcomes, and you come back to the lead when a real decision is needed.

6. Day to day with the CTO

Real asks from daily use, lightly edited:

  • Status, without starting work: "How are we doing on the storage migration? Just give me a status update, don't do more work." / "Has our chief of staff done anything yet?"
  • What runs where: "Can you tell me all the agents and sessions we have on the worker VM?" / "What's eating my CPU on the worker VM?" / "On the worker VM, which sessions can we put to sleep?"
  • Machine trouble, handled by the agents: "The laptop is running out of space. Message all the live and recent sessions there, ask them to reclaim disk space, and give me a report with each session and its answer."
  • Models and workers: "Can we change homelab agent 3 to use agy with Gemini Flash?" / "Protect Claude so it stops being used for workers. No, protect it at the provider level." / "Pause the argon worker: its price is about to go up. Don't delete it."
  • Settings: "Change the merger's idle limit to 30 minutes." / "Put the research loop on hold."
  • When something is wrong: "The research project is stuck. Analyse why." / "I can't find my homelab session!", then "Report it to agent-net: it's a problem that it disappears from my list."
  • Clearing things for you: "Approve all the pending drafts for me." / "In my inbox I have 10 really old messages from one project. Get rid of them."
  • Finding out what it can do: "What do you know about your abilities?" The CTO lists what it can do for you, and what it would have to ask agent-net to build.

How to talk to the CTO

  • Do not approve twice. If you already asked for something, the CTO acts on it. If it asks you to authorise what you just said, tell it: that is a defect, not your job.
  • Make it the default. When you repeat a choice, ask the CTO to make it the default or a standing rule, so no one asks again.

7. Connect Grok Bot (optional)

Cloud agents such as Grok Bot can use agent-net too, through MCP.

  1. In the TUI, open Settings (tab 5) and select Connected apps. Press p to turn internet access on. With Tailscale, agent-net sets up the route for you. The status line shows the public MCP URL.
  2. In Grok, add an MCP connector with that URL.
  3. Grok shows a code. Approve it in Connected apps, as a bot (it acts under its own name, with a small set of tools) or as an owner app (it acts as you).

Details: reference.md.

8. When something goes wrong

Most problems are found and fixed without you. The CTO watches a list of problems, such as a machine that went silent, a session that is stuck or a failing merge queue, and raises only what needs you.

When you notice something yourself:

  • Ask for the cause, not a workaround. "The research project is stuck. Analyse why." The CTO reads the machine logs and the history of every message, worker and change, and tells you what broke.
  • If agent-net itself is at fault, have it fixed. "Report it to agent-net." The agent-net lead gets the evidence, a worker fixes it, and the fix ships in the next release. Every machine updates itself.
  • Some causes are physical, and those are yours: a machine that is off or asleep, an expired sign-in, a network route to approve. The CTO tells you which one it is.

Known problems and their fixes: troubleshooting.md.

Security model

The short version. The full model, including what is not protected, is in docs/security.md.

  • Built for machines you own, on a LAN or a Tailscale network. Do not expose the gateway port (7420) to the internet.
  • A machine joins with a one-time code (10 minutes, one use) and the SHA-256 of the gateway's CA. Traffic is TLS with the gateway's own CA, and each machine has its own token.
  • The daemon checks which local process is calling, from the kernel's view of the caller's process.
  • A message from another agent is never your approval. Changes you ask for in the CTO chat run at once, with your words checked. Changes the CTO wants without your words wait for you on the Desk.
  • The CTO's messages are not reviewed by Claude Code's auto-mode check; each receiving agent's charter and permission checks still apply.
  • Connected apps: off by default. Each app is approved by you in the TUI with a one-time code, gets only its own tools, and is rate limited. Revoke it with x.
  • The guidance agent-net adds to your instruction files is advice to the model, not enforcement.
  • Not protected: a compromised enrolled machine, prompt injection carried in a message, and any process running as your user.

Lifecycles

A lifecycle is the list of states something can be in, and the events that move it from one state to the next. A message, for example, is first stored, then delivered, then replied to.

agent-net uses lifecycles to answer three everyday questions about any piece of work: where is it now, who has to act next, and what happens if nobody does. The screens you use (the Desk, Sessions, Workers), the reminders sent to agents and the alerts to the CTO all read these states. When something is stuck, its state tells you where.

        Principles

        The rules agent-net is built on. When a design choice is unclear, these decide it. They are kept up to date; the early brief (brief.md) is history. Where a principle is a goal that the product does not fully meet yet, it says so.

        The network

        1. Connect agents, do not replace them. Every agent keeps its own harness, model, permissions and context. agent-net carries messages, wakes sessions and records work; it is not one big agent. Harness-specific code lives in adapters.
        2. Each agent owns a whole piece. One agent per product, library or service, which it can change end to end. Never split agents by layer (a backend agent and a frontend agent): that shares one product's context across a line that should not exist.
        3. Specialize, do not centralize. Many agents with narrow charters do repeated work better than one agent that does everything. A charter says what the agent does, accepts and refuses, and when it must ask.

        The owner's place in the loop

        1. Near the loop is the default, and the target. Agents work on their own and stop only at a decision that needs you, with a result and a recommendation: workers, peer messages and delivery steps all work this way. Two other ways exist, each for a reason:
          • Out of the loop, to scale a mature project: an agent works toward its charter's purpose on a schedule and nobody prompts it. Standing loops (decision 0094) do this today for any project you give a loop.
          • In the loop, for micromanagement or a crisis: you prompt an agent in a terminal and read every turn. It is the exception, not the way to work.
        2. Your attention is the scarce resource. An ask reaches you only when it saves you time compared with opening the session yourself, and it comes with a recommendation. So you keep only what is truly yours: deleting data, spending money, secrets that can spend money, approving a new connected app or device, and choices about how you work. Everything reversible is decided by the agents and logged. The chief of staff sorts the asks for you.
        3. Agents can do what you can do. Every action you can take in the TUI should have an equivalent the CTO can take for you, except the decisions in principle 5, which it can prepare but not make. Most have one today; the gaps are listed in reference.md and are closed as they are found.
        4. No limits you did not ask for. agent-net adds no approval gate, cap or refusal unless you asked for it. Agents may propose one; proposing is not adding.

        Trust and evidence

        1. Work leaves evidence. A change moves through delivery steps (accept, test, merge, release and verify, plus review for riskier changes). Each step has an owner and records what it checked. A fix starts with a reproduction and a failing test. How independent a review must be is your setting; by default any review counts (decision 0083).
        2. The network learns. Your corrections and decisions go into one memory that agents search before they ask. Each worker model builds a track record, and the picker uses it.

        Seeing what runs

        1. Measure everything that runs, and watch it. The gateway counts every protocol request by origin and method. A number nobody reads finds nothing: a sharp rise in one origin's load should reach the agent that can fix it, without waiting for someone to look.
        2. Show what agents do in plain words. A long run of tool calls should read as a few sentences, with the raw calls one step away. A summary helps you watch; it never replaces review of the result.
        3. Know exactly what your agents run. Every skill, prompt and agent definition a session runs can be read in agent-net and traced to its source and version. Imported skills can today; prompts and agent definitions are on the roadmap.
        4. One source for each capability. A skill, prompt or agent definition has one stored source. Copies can be rebuilt from it, and a copy that changes is either brought back or saved as a new version, never left as a silent fork. Today imported skills work this way; prompts and agent definitions are on the roadmap.

        Building it

        1. Performance first. A feature that loads the gateway or the machine heavily is not done. Load data for what is on screen, push changes instead of polling, and measure before and after.
        2. Verify in the real setup. A change is done when it works the way you will use it, measured on the real machines, not only in tests.
        3. Smart defaults, everything changeable. Every role, model, rule and screen setting has a working default and can be changed by you, and most of them by the CTO for you.
        4. Plain words. Docs, messages and screens use short sentences and concrete words.
        5. Each decision is made in one place. Which model runs a worker, who leads a repo, whether a tool may run, where a message goes: for each such question, one place in the code decides. When two places decide the same thing, they drift apart, and two agents get two different answers. That is a bug, found and fixed like any other (decision 0163).

        Proposed: execution drivers

        A proposal to separate the daemon from the execution layer, so other engines (for example an OpenRig team) can plug in. Nothing here is built.
